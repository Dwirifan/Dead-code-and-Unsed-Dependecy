# 4.3 Perancangan Sistem
Perancangan sistem dilakukan untuk menerjemahkan kebutuhan fungsional dan non-fungsional yang telah dirumuskan pada Subbab 4.1 ke dalam rancangan teknis sebelum sistem diimplementasikan. Pada tahap ini, sistem dirancang menggunakan pendekatan pipeline modular, yaitu alur pemrosesan yang membagi sistem ke dalam beberapa modul dengan tanggung jawab yang terpisah.

Pendekatan pipeline modular digunakan agar setiap komponen dapat dikembangkan, diuji, dan diperbaiki secara mandiri tanpa mengganggu keseluruhan sistem. Perancangan sistem dalam penelitian ini meliputi arsitektur sistem, struktur data, algoritma inti, alur kerja sistem, mekanisme keamanan prosedural, serta antarmuka output.

### 4.3.1 Perancangan Arsitektur Sistem
Sistem dirancang menggunakan arsitektur pipeline modular. Pada arsitektur ini, keluaran dari satu modul menjadi masukan bagi modul berikutnya. Alur tersebut dimulai dari proses pembacaan proyek, pembentukan AST, pembangunan dependency graph, analisis kode, proses eliminasi, hingga pembuatan laporan. Dengan rancangan ini, setiap modul memiliki fungsi yang jelas dan dapat diuji secara terpisah.

Secara umum, arsitektur sistem terdiri dari lima komponen utama, yaitu:
1. Modul Pengurai (Parser): Bertugas membaca kode sumber dan package.json, membentuk AST, serta menyimpan hasil parsing ke dalam cache untuk menghindari pemrosesan berulang.
2. Mesin Pemetaan (Graph Builder): Bertugas mengidentifikasi entry point dan membangun dependency graph berdasarkan relasi import, export, dan require.
3. Mesin Analisis dan Penelusuran (Analyzer): Bertugas menganalisis AST dan dependency graph untuk mendeteksi dead code, dead file, dan unused dependency melalui BFS, scope analysis, serta klasifikasi tingkat keyakinan temuan.
4. Modul Eksekusi dan Modifikasi (Eliminator): Bertugas menangani temuan yang telah dikonfirmasi pengguna melalui empat tingkat operasi: Level 0 (Pasif), Level 1 (Lazy Load), Level 2 (Empty Body), dan Level 3 (Aggressive). Modul ini juga menangani pembersihan dependensi, pembuatan patch diff, serta mekanisme backup/restore.
5. Generator Pelaporan dan Antarmuka (UI & Reporting): Bertugas menampilkan hasil analisis melalui CLI, menyajikan ringkasan temuan, dan mengekspor laporan visual berbasis HTML.

### 4.3.2 Perancangan Struktur Data
Sistem ini merupakan utilitas CLI untuk analisis statis, sehingga struktur data dirancang untuk beroperasi di dalam memori (in-memory) selama satu siklus eksekusi berlangsung. Sistem tidak menggunakan basis data eksternal karena data hanya dibangun, ditelusuri, dan diproses sementara selama proses analisis berjalan. Pendekatan ini digunakan agar sistem tetap ringan dan tidak meninggalkan data tambahan pada proyek pengguna.

Secara umum, struktur data utama yang digunakan dalam sistem meliputi Abstract Syntax Tree (AST), Lexical Scope Record, Project Dependency Graph, dan Dead Node Object. Selain itu, sistem juga menggunakan beberapa struktur pendukung seperti ParseCache, DeclarationInfo, Edge, dan GlobalRegistry untuk mendukung penyimpanan sementara, pencatatan deklarasi, pemetaan relasi, serta analisis lintas berkas. Gambar 4.2 Class diagram struktur data

**A. Abstract Syntax Tree (AST)**
Abstract Syntax Tree (AST) merupakan struktur data yang digunakan untuk merepresentasikan kode sumber dalam bentuk pohon sintaksis. Setiap berkas .js, .ts, .jsx, dan .tsx diurai (parsed) menggunakan @typescript-eslint/typescript-estree agar sistem dapat membaca struktur kode tanpa menjalankan program target. Struktur AST menjadi dasar bagi proses penelusuran deklarasi, pemanggilan fungsi, impor, ekspor, serta elemen kode lain yang diperlukan dalam analisis statis.

Untuk meningkatkan efisiensi pemrosesan, hasil parsing setiap berkas dapat disimpan sementara ke dalam ParseCache menggunakan struktur Map berbasis jalur berkas (file path) sebagai kunci. Dengan mekanisme ini, berkas yang sama tidak perlu diurai ulang apabila dibutuhkan kembali dalam satu siklus eksekusi. Komponen utama representasi pohon AST ditunjukkan pada Tabel 4.1.

Tabel 4.1 Komponen Utama Representasi Pohon AST (ESTree Format)

| Komponen Utama | Representasi Objek / Tipe | Deskripsi |
| :--- | :--- | :--- |
| Root Node | Program | Simpul utama yang mewakili keseluruhan isi berkas kode sumber |
| Branch Nodes | FunctionDeclaration, IfStatement, ClassDeclaration, ImportDeclaration, ExportNamedDeclaration | Simpul percabangan logika atau blok cakupan (scope) tertentu yang masih memiliki simpul anak (child nodes) di bawahnya. |
| Leaf Nodes | Identifier, Literal | Simpul akhir yang merepresentasikan nama, nilai, atau literal tertentu di dalam kode. |
| Metadata Posisi | Atribut loc (start.line, end.line) | Informasi posisi kode yang digunakan untuk menelusuri lokasi temuan dan membantu proses modifikasi kode secara presisi. |

**B. Lexical Scope Record**
Setelah AST terbentuk, sistem membangun Lexical Scope Record untuk setiap berkas melalui kelas Scope. Struktur ini digunakan untuk merepresentasikan hierarki cakupan leksikal, mulai dari cakupan global, fungsi, hingga blok kode tertentu. Setiap objek Scope menyimpan referensi ke cakupan induknya (parent scope) sehingga membentuk scope chain. Mekanisme ini memungkinkan sistem menelusuri penggunaan identifier secara bertingkat untuk membedakan identifier yang digunakan, tidak digunakan, atau hanya diberi nilai tetapi tidak pernah dibaca.

Informasi deklarasi identifier disimpan dalam struktur declarations berbasis Map. Nama identifier, seperti counter atau fetchData, digunakan sebagai kunci, sedangkan nilainya berupa objek DeclarationInfo yang memuat detail deklarasi. Atribut utama yang digunakan dalam Lexical Scope Record ditunjukkan pada Tabel 4.2.

Tabel 4.2 Atribut DeclarationInfo pada Lexical Scope Record

| Atribut | Tipe Data | Deskripsi |
| :--- | :--- | :--- |
| type | String | Tipe deklarasi (Variable, Function, atau Class). |
| line | Integer | Nomor baris tempat identifier dideklarasikan. |
| node | Object | Referensi langsung ke simpul AST yang bersangkutan. |
| parentNode | Object | Referensi ke simpul AST induk dari identifier, digunakan untuk menentukan konteks deklarasi, misalnya berada di dalam VariableDeclaration atau ImportDeclaration. |
| used | Boolean | Status penggunaan identifier. Nilai true menunjukkan identifier pernah digunakan atau dibaca, sedangkan nilai false menandakan kandidat dead code. |
| readCount | Integer | Jumlah total pembacaan identifier. Hanya operasi read yang menaikkan nilai ini. |
| writeCount | Integer | Jumlah penulisan atau pemberian nilai terhadap identifier. |

Untuk mengurangi kesalahan klasifikasi, sistem menggunakan properti selfName pada cakupan fungsi untuk mengenali pemanggilan rekursif. Melalui struktur ini, identifier dengan used: false dan readCount: 0 dikategorikan sebagai kandidat unused, sedangkan identifier dengan writeCount > 0 tetapi readCount: 0 dikategorikan sebagai write-only dead code. Hasil klasifikasi tersebut kemudian dikonsolidasikan ke dalam Dead Node Object untuk diproses pada tahap berikutnya.

**C. Project Dependency Graph**
Project Dependency Graph merupakan struktur data yang merepresentasikan hubungan ketergantungan antarberkas dalam proyek. Struktur ini dibangun melalui fungsi buildProjectGraph dengan algoritma Breadth-First Search (BFS). Proses penelusuran dimulai dari entry point, kemudian sistem melacak relasi import, export, dan require yang ditemukan pada AST setiap berkas.

Pemetaan ini membentuk graf terarah (directed graph) yang digunakan untuk mengidentifikasi berkas yang tidak terjangkau dari entry point sebagai dead files. Selain itu, struktur ini juga mencatat paket NPM yang benar-benar direferensikan oleh kode sumber untuk mendeteksi unused dependencies. Komponen utama Project Dependency Graph ditunjukkan pada Tabel 4.3.

Tabel 4.3 Komponen, Atribut, dan Properti Data Project Dependency Graph

| Komponen/Properti | Tipe Data | Deskripsi |
| :--- | :--- | :--- |
| liveFiles | Set<String> | Menyimpan jalur berkas yang berhasil dijangkau dari entry point. Berkas yang tidak termasuk dalam himpunan ini diklasifikasikan sebagai dead file |
| Edges | Array of Object | Menyimpan relasi ketergantungan antarberkas dengan skema { from, to, names }, yaitu berkas pengimpor, berkas yang diimpor, dan nama ekspor yang digunakan. |
| usedPackages | Set<String> | Menyimpan nama paket NPM yang direferensikan oleh kode sumber sebagai pembanding terhadap package.json untuk mendeteksi unused dependencies. |
| unsafeFiles | Set<String> | Menyimpan berkas yang mengandung pola dinamis, seperti eval(), WithStatement, atau computed property access, sehingga perlu dikecualikan dari penghapusan otomatis. |
| globalRegistry | Object | Menyimpan data global lintas berkas yang digunakan untuk membantu proses analisis. |
| globalRegistry.usedExports | Map<String, Set<String>> | Memetakan berkas terhadap daftar fungsi atau variabel ekspor yang digunakan oleh berkas lain. |
| globalRegistry.calledMethods | Set<String> | Menyimpan nama method kelas yang dipanggil di seluruh proyek untuk validasi unused class methods. |

**D. Dead Node Object**
Dead Node Object merupakan struktur data final berbentuk array of objects yang dihasilkan oleh Mesin Analisis setelah proses pemindaian proyek selesai. Struktur ini berperan sebagai kontrak data (data contract) yang menghubungkan Mesin Analisis, Modul Eliminator, dan Generator Pelaporan. Seluruh temuan kode mati dikonsolidasikan ke dalam struktur ini sehingga dapat digunakan sebagai sumber data utama untuk proses penghapusan, validasi, dan penyajian laporan.

Setiap objek di dalam array memuat informasi mengenai identitas temuan, lokasi kode, tingkat keyakinan analisis, serta rekomendasi tindakan. Rincian atribut utama Dead Node Object ditunjukkan pada Tabel 4.4.

#### 4.3.3 Perancangan Algoritma Inti

Bagian ini menguraikan algoritma utama yang digunakan dalam sistem untuk melakukan analisis *dead code* dan *unused dependency*. Sistem bergantung pada dua pendekatan komputasional utama, yaitu pencarian graf untuk melacak keterhubungan antarberkas dan penelusuran struktur sintaksis untuk menganalisis isi setiap berkas.

##### A. Algoritma Keterlacakan Berkas BFS

Untuk memetakan keterhubungan antarberkas dalam proyek, sistem menerapkan algoritma *Breadth-First Search* (BFS). Algoritma ini digunakan karena mampu menelusuri *dependency graph* secara melebar dan sistematis dari titik awal (*entry point*) menuju berkas-berkas lain yang saling terhubung.

Proses keterlacakan berkas menggunakan BFS dilakukan melalui langkah-langkah berikut:

1. **Inisialisasi:** Sistem menetapkan berkas utama, seperti `index.js`, `main.ts`, atau *entry point* yang didefinisikan, sebagai simpul awal (*root node*) dan memasukkannya ke dalam antrean (*queue*).

2. **Eksplorasi Berkas:** Selama antrean tidak kosong, sistem mengambil berkas pertama dari antrean (*dequeue*) untuk dianalisis.

3. **Ekstraksi Impor:** Sistem membaca deklarasi `import`, `export`, atau `require` pada berkas tersebut untuk menemukan berkas dependensi yang terhubung.

4. **Penandaan dan Pembaruan Antrean:** Berkas dependensi yang baru ditemukan ditandai sebagai `visited` untuk mencegah perulangan (*infinite loop*) akibat *circular dependency*, kemudian dimasukkan ke dalam antrean BFS.

5. **Identifikasi Berkas Tidak Terpakai:** Setelah proses penelusuran selesai, berkas yang tidak masuk ke dalam daftar `visited` diklasifikasikan sebagai *dead file* karena tidak memiliki jalur keterhubungan dari *entry point*.

##### B. Algoritma Penelusuran AST (AST Traversal)

Setelah keterhubungan antarberkas dipetakan, sistem melakukan analisis pada tingkat sintaksis untuk mendeteksi variabel, fungsi, impor, atau dependensi yang tidak digunakan di dalam berkas (in-file dead code). Analisis ini dilakukan melalui algoritma penelusuran Abstract Syntax Tree (AST Traversal), yaitu proses mengunjungi simpul-simpul AST secara rekursif untuk membaca struktur kode tanpa menjalankan program.

**Gambar 4.4 Activity Diagram Algoritma Penelusuran AST**

1. Pembentukan Pohon Sintaksis (Parsing): Kode sumber diurai (parsed) menjadi struktur AST. Pada tahap ini, sistem juga menyiapkan tabel referensi untuk menyimpan daftar deklarasi yang ditemukan.
2. Pendaftaran Deklarasi (Registration): Sistem menelusuri AST dari simpul awal dan mencatat deklarasi seperti variabel, fungsi, parameter, kelas, atau impor ke dalam tabel referensi dengan status awal belum digunakan.
3. Pelacakan Penggunaan (Identifier Tracking): Saat menemukan penggunaan identifier pada simpul ekspresi, sistem mencocokkannya dengan tabel referensi dan memperbarui statusnya sebagai telah digunakan.
4. Penelusuran Rekursif (Recursive Traversal): Jika suatu simpul memiliki simpul anak (child nodes), sistem melanjutkan penelusuran secara rekursif hingga seluruh cabang AST selesai diperiksa.
5. Evaluasi dan Penyaringan Akhir (Final Filtering): Setelah seluruh simpul ditelusuri, sistem mengevaluasi tabel referensi. Entitas yang tetap berstatus belum digunakan diklasifikasikan sebagai dead code atau unused dependency untuk diproses pada tahap berikutnya.

Alur kerja sistem dirancang menggunakan arsitektur pipeline yang beroperasi secara sekuensial dan semi-otomatis. Perancangan alur sistem ini dibagi menjadi dua bagian, yaitu diagram arsitektur pipeline yang menjelaskan aliran data antar-modul, serta activity diagram CLI yang menjelaskan urutan interaksi pengguna dengan sistem.

5. **Eksekusi Keputusan:** Jika pengguna menolak, sistem membatalkan proses modifikasi. Jika pengguna menyetujui, sistem membuat backup, menjalankan Modul Eliminator, memperbarui package.json, mengekspor laporan HTML, dan menyelesaikan program.

### 4.3.5 Perancangan Mekanisme Keamanan Prosedural
Mekanisme keamanan prosedural dirancang menggunakan pendekatan semi-otomatis (user-in-the-loop) sebagai lapisan pengaman sebelum proses penghapusan dilakukan. Pendekatan ini diterapkan karena sistem bekerja dengan metode analisis statis, yaitu menganalisis kode tanpa menjalankan program secara langsung. Oleh karena itu, sistem memiliki keterbatasan dalam mengenali pola dinamis seperti eval(), dynamic imports, callback, atau manipulasi objek global yang baru diketahui saat runtime.

Untuk menjaga integritas proyek pengguna, sistem tidak langsung menghapus kode yang terindikasi tidak digunakan. Mekanisme konfirmasi pada terminal dirancang berdasarkan tiga prinsip utama berikut:

1. **Pencegahan Kesalahan Positif (False-Positive Prevention):** Sistem menampilkan ringkasan metrik temuan sebelum Modul Eliminator dijalankan. Dengan demikian, pengguna dapat membatalkan proses apabila terdapat berkas atau kode yang sebenarnya masih digunakan secara dinamis, tetapi terdeteksi sebagai kode mati oleh sistem.
2. **Pemaparan Status Risiko (Risk Status Exposure):** Sistem memanfaatkan data unsafeFiles dan atribut status pada Dead Node Object untuk menampilkan kategori risiko, seperti safe, review, atau risky. Kategori ini membantu pengguna membedakan temuan yang aman dihapus dan temuan yang perlu ditinjau secara manual.
3. **Integritas Pemulihan (Rollback Integrity):** Sebelum proses penghapusan dilakukan, sistem membuat cadangan (backup) proyek. Mekanisme ini memungkinkan pengguna mengembalikan proyek ke kondisi semula apabila terjadi kesalahan atau perubahan yang tidak diinginkan setelah proses pembersihan.

Dengan rancangan tersebut, proses penghapusan kode mati tidak berjalan sepenuhnya otomatis, tetapi tetap melibatkan validasi pengguna agar keamanan dan integritas proyek tetap terjaga.

### 4.3.6 Perancangan Antarmuka Output
Antarmuka output dirancang dalam dua bentuk, yaitu luaran terminal melalui Command Line Interface (CLI) dan dokumen visualisasi HTML interaktif. Luaran terminal digunakan untuk menampilkan ringkasan analisis secara cepat serta menangani konfirmasi pengguna, sedangkan dokumen HTML digunakan untuk menyajikan hasil pemetaan proyek secara visual dan lebih mudah ditelusuri.

**A.   Antarmuka Terminal (CLI Output)**
Antarmuka terminal dirancang untuk menyajikan hasil analisis secara terstruktur langsung di dalam lingkungan baris perintah. Luaran terminal ini terdiri dari beberapa elemen utama:
1. **Ringkasan Statistik (Scan Summary):** Menampilkan metrik hasil pemindaian, seperti jumlah berkas yang dianalisis, jumlah dead files, total temuan, dan waktu eksekusi analisis.
2. **Kategorisasi Temuan Berdasarkan Status Keamanan:** Mengelompokkan temuan ke dalam status safe, review, dan risky. Setiap temuan dilengkapi informasi lokasi baris, nama entitas, tipe anomali, dan tingkat keyakinan (confidence level).
3. **Dialog Persetujuan Interaktif:** Pada mode penindakan, sistem menampilkan pratinjau perubahan dan meminta konfirmasi pengguna sebelum modifikasi berkas dilakukan.
4. **Laporan Dependensi:** Menampilkan daftar dependensi NPM yang terdeteksi tidak digunakan, termasuk perbandingan antara dependensi yang dideklarasikan dan dependensi yang benar-benar digunakan.

**B.    Dokumen Visualisasi HTML Interaktif (Dashboard)**
Dokumen HTML interaktif dirancang sebagai luaran baca-saja (read-only) untuk membantu pengguna memahami struktur proyek secara visual. Luaran ini tidak digunakan untuk mengeksekusi penghapusan kode, tetapi berfungsi sebagai media pelaporan dan validasi hasil analisis. Melalui visualisasi ini, pengguna dapat melihat hubungan antarberkas, dependensi aktif, dependensi tidak terpakai, serta temuan kode mati dalam bentuk yang lebih terstruktur.

Secara umum, dokumen visualisasi HTML terdiri dari beberapa elemen utama:
1. **Kepala Halaman (Header):** Menampilkan identitas perangkat lunak dan ringkasan utama, seperti jumlah berkas aktif, dependensi terpakai, dan dependensi tidak terpakai.
2. **Bilah Statistik (Statistics Strip):** Menyajikan metrik utama dalam bentuk kartu statistik, seperti total berkas aktif, jumlah koneksi graf, dan total dependensi proyek.
3. **Panel Graf Interaktif:** Menampilkan graf ketergantungan antarberkas dengan dukungan interaksi seperti zoom, drag, dan penyorotan hubungan antar-node.
4. **Panel Samping (Sidebar):** Menyediakan legenda direktori, daftar dependensi yang digunakan, dan daftar dependensi yang tidak digunakan.
5. **Bagian Laporan Kode Mati:** Menampilkan tabel temuan berdasarkan kategori safe, review, dan risky. Setiap temuan memuat informasi nama berkas, nomor baris, nama entitas, tipe anomali, tingkat keyakinan, dan status keamanan.
6. **Fitur Pendukung Aksesibilitas:** Menyediakan dukungan dua bahasa serta mode tampilan gelap dan terang (dark/light mode) untuk menyesuaikan preferensi pengguna.
