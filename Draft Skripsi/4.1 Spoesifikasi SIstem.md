# 4.1 Spesifikasi Sistem

Subbab ini memaparkan hasil tahap perencanaan (*planning*) pada metode *Extreme Programming* (XP), yang meliputi spesifikasi kebutuhan sistem, *user stories*, kriteria penerimaan, dan rencana iterasi pengembangan.

### 4.1.1 Kebutuhan Fungsional
Kebutuhan fungsional mendefinisikan kapabilitas dan fitur utama yang wajib diakomodasi oleh sistem. Kebutuhan tersebut meliputi:
1. Sistem harus mampu melakukan pemindaian ( parsing ) terhadap berkas manifes package.json dan membedah struktur kode berformat .js dan .ts menjadi bentuk pohon hierarki AST.
2. Sistem harus memiliki algoritma penelusuran (*traversal*) untuk membangun grafik ketergantungan (*dependency graph*) guna mendeteksi pustaka yang tidak memiliki jalur pemanggilan, serta mengidentifikasi anomali arsitektur seperti dependensi melingkar (*circular dependency*).
3. Sistem harus mampu menganalisis AST untuk mendeteksi *dead code* (termasuk *wasted computation*) dan *unused dependency*.
4. Sistem harus menerapkan mekanisme semi-otomatis melalui penyajian peringatan konfirmasi persetujuan pengguna (*prompt*) di antarmuka terminal sebelum mengeksekusi penghapusan kode.
5. Sistem harus mampu mengekspor (*generate*) hasil analisis ke dalam bentuk dokumen visual HTML interaktif sebagai laporan pemetaan struktur proyek.

### 4.1.2 Kebutuhan Non Fungsional
Kebutuhan non-fungsional mendefinisikan standar mutu operasional sistem, yang dalam penelitian ini mengacu pada standar kualitas ISO/IEC 25010.
1. Performance Efficiency: Sistem harus memindai dan mengeksekusi pembersihan kode dengan cepat dan ringan, murni menggunakan analisis statis tanpa memicu overhead memori dari eksekusi runtime [8].
2. Maintainability: Sistem harus dikembangkan menggunakan arsitektur modular yang mematuhi prinsip Clean Code, sehingga logika parser dan antarmuka CLI dapat dipelihara dan dimodifikasi dengan mudah di masa mendatang [9].
3. Reliability: Sistem tidak diperbolehkan memodifikasi atau menghapus berkas kode sumber pengguna tanpa melalui konfirmasi eksplisit terlebih dahulu. Setiap operasi penghapusan harus didahului oleh pencadangan otomatis (backup) sebagai mekanisme pemulihan jika terjadi kesalahan [10].
4. Portability: Sistem harus dapat dijalankan pada lingkungan yang memiliki runtime Node.js tanpa memerlukan instalasi dependensi tambahan di luar yang telah didefinisikan di dalam berkas package.json proyek [11].

### 4.1.3 User Story dan Kriteria Penerimaan (acceptance test criteria)
Berdasarkan kebutuhan fungsional dan non-fungsional yang telah dirumuskan, kebutuhan pengguna disusun dalam bentuk user stories. Setiap user story dilengkapi dengan kriteria penerimaan (acceptance test criteria) sebagai acuan untuk menilai keberhasilan fitur yang dikembangkan.

| ID | User Story | Kriteria Penerimaan |
| :--- | :--- | :--- |
| US-01 | Sebagai pengembang, saya ingin sistem dapat membaca proyek JavaScript dan TypeScript agar berkas sumber dan konfigurasi proyek dapat dikenali. | Sistem mampu membaca package.json serta memindai berkas .js dan .ts. |
| US-02 | Sebagai pengembang, saya ingin sistem dapat membentuk Abstract Syntax Tree (AST) agar struktur kode dapat dianalisis tanpa menjalankan program. | Sistem mampu melakukan parsing kode sumber dan menghasilkan AST yang dapat ditelusuri. |
| US-03 | Sebagai pengembang, saya ingin sistem dapat membangun dependency graph agar relasi antarberkas dan dependensi dapat dipetakan. | Sistem mampu membaca relasi import, export, dan require, lalu membentuk graf ketergantungan antarmodul. |
| US-04 | Sebagai pengembang, saya ingin sistem dapat mendeteksi kode, berkas, dan dependensi yang berpotensi tidak digunakan agar struktur proyek menjadi lebih efisien. | Sistem mampu mengidentifikasi dead code, dead file, unused dependency, serta anomali arsitektur (circular dependency). |
| US-05 | Sebagai pengembang, saya ingin sistem menyediakan konfirmasi sebelum penghapusan agar perubahan kode tetap berada di bawah kendali pengguna. | Sistem menampilkan status temuan dan prompt konfirmasi sebelum proses penghapusan dilakukan. |
| US-06 | Sebagai pengembang, saya ingin sistem menampilkan hasil analisis melalui CLI dan laporan HTML agar hasil deteksi mudah dibaca dan divalidasi. | Sistem mampu menampilkan ringkasan hasil pada CLI serta mengekspor laporan visual HTML yang memuat relasi proyek dan daftar temuan. |

### 4.1.4 Rencana Iterasi Pengembangan
Berdasarkan *user stories* dan kriteria penerimaan yang telah dirumuskan, serta mengacu pada tahap perencanaan iterasi dalam metode XP sebagaimana dijelaskan pada Bab 3, proses pengembangan sistem dibagi ke dalam beberapa iterasi berikut. Rencana iterasi pengembangan disusun berdasarkan *user stories* dan kebutuhan sistem. Pembagian iterasi dilakukan agar proses pengembangan berjalan secara bertahap, terukur, dan sesuai dengan karakteristik Extreme Programming (XP) yang menekankan pengembangan inkremental, pengujian berkelanjutan, dan perbaikan kode secara iteratif.

| Iterasi | Fokus Pengembangan | User Story Terkait | Hasil yang Diharapkan |
| :--- | :--- | :--- | :--- |
| Iterasi 1 | Pembangunan Core Parser | US-01, US-02 | Sistem mampu membaca proyek dan mengubah kode sumber menjadi AST yang dapat ditelusuri. |
| Iterasi 2 | Pembangunan Graph Builder | US-03 | Sistem mampu melakukan parsing kode sumber dan menghasilkan AST yang dapat ditelusuri. |
| Iterasi 3 | Pembangunan Analyzer dan Eliminator | US-04, US-05 | Sistem mampu mendeteksi dead code, dead file, unused dependency, menangani resolusi hoisting, serta menyiapkan proses penghapusan secara aman. |
| Iterasi 4 | Implementasi CLI dan Mekanisme Konfirmasi | US-05, US-06 | Sistem mampu menampilkan hasil analisis melalui terminal dan menyediakan prompt konfirmasi sebelum penghapusan. |
| Iterasi 5 | Implementasi HTML Report dan Integrasi Akhir | US-06 | Sistem mampu menghasilkan laporan HTML interaktif dan mengintegrasikan seluruh modul menjadi sistem yang siap diuji. |

Pada setiap iterasi, implementasi dilakukan melalui perencanaan tugas, pengkodean, pengujian awal, self-review/code walkthrough, refactoring, integrasi, dan penetapan hasil ke production baseline. Mekanisme ini digunakan untuk menjaga stabilitas kode sebelum modul digunakan pada iterasi berikutnya.
