BAB ARSITEKTUR & PENJELASAN MODUL (Untuk Skripsi)
================================================

DeadKiller dirancang menggunakan arsitektur Modular / Single Responsibility Principle (SRP).
Tujuannya agar sistem sangat scalable: jika ada sintaks JavaScript/TypeScript baru di masa depan,
kita hanya perlu menambahkan satu file modul tanpa mengganggu stabilitas Core Traversal Engine.

────────────────────────────────────────────────
1. MODUL DEPENDENCY (NPM Packages)
────────────────────────────────────────────────
  src/analyzer/dependency/dependencyAnalyzer.js
  Tugas: Modul ini terpisah murni untuk menganalisis package.json.
  - Membaca daftar `dependencies` (runtime dependencies).
  - Melewatkan (bypass) `devDependencies` karena mereka adalah alat bantu (webpack, prettier)
    yang dipanggil via CLI, bukan melalui import di dalam source code.
  - Membandingkan daftar dependencies dengan `usedPackages` hasil dari Graph BFS.

────────────────────────────────────────────────
2. MODUL DEAD CODE (AST Traversal)
────────────────────────────────────────────────
  Logika deteksi "Dead Code" dipecah menjadi 1 Orkestrator dan 6 File Pasukan Khusus:

  [Orkestrator Utama]
  ├── deadCodeAnalyzer.js
  │   Tugas: Core Traversal Loop. Menelusuri Abstract Syntax Tree (AST) secara keseluruhan.
  │   Ibarat "Pabrik Utama", file ini yang memetakan Scope, mendaftar semua Identifier, 
  │   dan memanggil fungsi detektif dari file-file di bawah ini.

  [Pasukan Khusus / Helpers]
  ├── scope.js & scopeHelpers.js
  │   Tugas: Mencatat siklus hidup variabel (Lexical Scoping). Ibarat memori RAM sementara.
  │
  ├── isReference.js
  │   Tugas: Membedakan mana "Deklarasi" (const a = 1) dan mana "Referensi" (console.log(a)).
  │   Sangat krusial untuk mencegah penghapusan variabel yang sedang dipakai.
  │
  ├── destructuringExtractor.js
  │   Tugas: Membedah sintaks JavaScript modern seperti `{ nama, umur } = user` atau `[a, b] = arr`.
  │
  ├── branchAnalyzer.js
  │   Tugas: Detektif untuk `UnreachableBranch` (misal kode di bawah `return` atau `if(false)`).
  │
  ├── logicAnalyzer.js
  │   Tugas: Detektif untuk `DuplicateCondition` (misal `if (x) {} else if (x) {}`).
  │
  └── exportAnalyzer.js
      Tugas: Menganalisis keamanan ekspor (lintas-modul) untuk `preserveExports` rule.

ALUR EKSEKUSI UTAMA (FLOW)
────────────────────────────────────────────────

1. USER menjalankan `deadkiller` (tanpa argumen)
   → bin/dce-cli.js → dynamic import wizard.js → showBanner → menu inquirer
   → user pilih aksi & folder → wizard spawn: `node dce-cli.js <cmd> <path>`

2. USER menjalankan `deadkiller scan <path>`
   → bin/dce-cli.js → commander.parse → scanCommand.action()
   → Jika FILE:  parseCode → findDeadCode → cetak laporan
   → Jika FOLDER: RuleEngine.loadConfig → buildProjectGraph (BFS)
                   → deteksi unused deps, dead files, dead code per file

3. USER menjalankan `deadkiller fix <path>`
   → bin/dce-cli.js → commander.parse → fixCommand.action()
   → Jika FILE:  parseCode → findDeadCode → removeDeadCode → generateDiff
                  → inquirer confirm → createBackup → tulis file baru
   → Jika FOLDER: buildProjectGraph → analisis semua file →
                   removeDeadCode per file → generateDiff per file →
                   inquirer checkbox (deps) → inquirer confirm →
                   createBackup → hapus dead files → tulis cleaned files →
                   removeUnusedDependencies

4. USER menjalankan `deadkiller visualize <path>`
   → buildProjectGraph → generateMermaidGraph(graph, rootDir, pkgData)
   → tulis HTML ke code-structure-trace.html → buka di browser

5. USER menjalankan `deadkiller history <path>`
   → listCheckpoints → inquirer pilih → restore/delete/batal

6. USER menjalankan `deadkiller show-deps <path>`
   → baca package.json → cetak dependencies & devDependencies

────────────────────────────────────────────────
PIPELINE ANALISIS DEAD CODE (4 FASE)
────────────────────────────────────────────────

findDeadCode(ast, fileName, globalRegistry, ruleEngine):

  Phase 1 — Scope Mapping (estraverse.traverse)
    ├── Buat Scope baru untuk setiap Function/Block
    ├── Catat deklarasi: VariableDeclarator, FunctionDeclaration,
    │   Parameter, ImportDeclaration → scope.addDeclaration()
    ├── Catat referensi: Identifier yang isReference() === true
    │   → scope.addReference()
    └── Destructuring ditangani oleh extractIdentifiers()
        `var` hoisting ditangani oleh findFunctionScope()

  Phase 2 — Export Cross-Module (markUsedExports)
    ├── Periksa ExportNamedDeclaration, ExportDefaultDeclaration
    ├── Cek globalRegistry.usedExports (dari projectGraph BFS)
    ├── Jika preserveExports ON di ruleEngine → amankan semua export
    └── Jika export dipakai di file lain → scope.markUsed(name)

  Phase 3 — Scope Resolution
    └── Setiap scope.resolve(): cocokkan references ↔ declarations
        Propagasi ke parent scope jika tidak ditemukan di scope lokal

  Phase 4 — Dead Code Collection
    ├── Kumpulkan variable/function yang !used (kecuali ignored)
    ├── Cerdas: jika SEMUA declarator di satu VariableDeclaration dead,
    │   hapus seluruh statement; jika sebagian → hapus individual
    ├── Tambahkan unreachable branches dari branchAnalyzer
    └── Return: [{name, type, line, node}]

KLASIFIKASI FITUR (3 KELOMPOK)
================================================

A — ANALISIS (Read-Only, Aman)
    scan <file>       : dead code 1 file
    scan <folder>     : dead code + dead files + unused deps (seluruh proyek)
    show-deps <folder>: lihat daftar dependensi
    visualize <folder>: HTML dashboard keterlacakan kode

B — TINDAKAN (Write + Backup Otomatis)
    fix <file>        : bersihkan 1 file, preview diff, 1x konfirmasi
    fix <folder>      : bersihkan proyek global, backup otomatis

C — PEMULIHAN (Safety Net)
    history <folder>  : lihat/restore/hapus checkpoint backup

PIPELINE AST 4 FASE (Inti Deteksi Dead Code)
================================================

  Input: Source Code (string)
    │
    ▼
  [astParser.js] → @typescript-eslint/typescript-estree
    │               Opsi: jsx:true, range:true, allowHashBang:true
    │               Support: JS, JSX, TS, TSX
    ▼
  Output: AST (Abstract Syntax Tree) berformat ESTree

  [deadCodeAnalyzer.js] → findDeadCode(ast, fileName, globalRegistry, ruleEngine)
    │
    ├─ FASE 1: Scope Mapping (estraverse.traverse)
    │    ├─ Buat Scope baru untuk setiap Function/Block
    │    ├─ Catat deklarasi: Variable, Function, Parameter, Import
    │    │   → scope.addDeclaration(name, type, line, node)
    │    ├─ Catat referensi: Identifier yang isReference() === true
    │    │   → scope.addReference(name)
    │    ├─ Destructuring → extractIdentifiers() menggali nama
    │    ├─ var hoisting → findFunctionScope() cari scope terdekat
    │    └─ Self-reference → scope.selfName untuk deteksi rekursi
    │
    ├─ FASE 2: Export Cross-Module (markUsedExports)
    │    ├─ Periksa ExportNamedDeclaration
    │    ├─ Periksa ExportDefaultDeclaration (function/class/identifier)
    │    ├─ Cek globalRegistry.usedExports (dari projectGraph BFS)
    │    └─ Jika preserveExports ON → amankan semua export
    │
    ├─ FASE 3: Scope Resolution
    │    └─ scope.resolve(): cocokkan references ↔ declarations
    │       Propagasi ke parent scope jika tidak ditemukan lokal
    │       Self-reference (rekursi) dilewati (scope.selfName)
    │
    └─ FASE 4: Dead Code Collection
         ├─ Kumpulkan variable/function yang !used (kecuali ignored)
         ├─ Jika SEMUA declarator dead → hapus seluruh statement
         │  Jika SEBAGIAN dead → hapus individual declarator
         ├─ Tambahkan unreachable branches dari branchAnalyzer
         │   (if(false), kode setelah return/throw/break/continue)
         └─ Return: [{name, type, line, node}]

MEKANISME KEAMANAN (Safety Net)
================================================

  1. BACKUP OTOMATIS
     Sebelum fix dijalankan, semua file yang akan diubah
     di-copy ke .deadkiller_backup/backup_<timestamp>/
     → User bisa restore kapan saja via "deadkiller history"

  2. PREVIEW DIFF
     Sebelum konfirmasi, user melihat diff berwarna
     di terminal — tahu persis apa yang akan berubah

  3. KONFIRMASI INTERAKTIF
     User harus tekan Y untuk menerapkan perubahan
     Untuk deps: user bisa uncheck deps yang tidak mau dihapus

  4. BAILOUT HEURISTICS (Dynamic Code)
     File dengan pola berisiko ditandai "unsafe":
     - eval()            → scope bisa berubah saat runtime
     - with()            → scope chain tidak deterministik
     - require(variable) → target import tidak diketahui statis
     - import(variable)  → target import dinamis
     - obj[variable]     → properti tidak diketahui statis
     File unsafe tetap di-analisis, tapi user diperingatkan

  5. RULE ENGINE (.deadkillerrc.json)
     User bisa konfigurasi:
     - ignorePrefixedVariables: ['_'] → abaikan _unused
     - preserveExports: true → jangan tandai export sebagai dead
     - preserveFiles: ['config.js'] → jangan tandai file tertentu

================================================
BATASAN & KELEMAHAN SISTEM (LIMITATION OF STUDY)
UNTUK BAB PEMBAHASAN TUGAS AKHIR
================================================
Dalam teori Analisis Statis (Static Code Analysis), mencapai tingkat kesempurnaan 100% adalah mustahil secara matematis (Halting Problem). Engine DeadKiller sengaja didesain konservatif untuk mengutamakan keamanan kode pengguna. Berikut adalah 4 batasan utama engine:

1. Properti Objek (MemberExpression Tree Shaking)
   - Masalah: Engine melacak 'Scope Variabel', bukan struktur internal objek. Jika ada `const config = { a: 1, b: 2 }; console.log(config.a);`, engine akan menganggap seluruh objek `config` terpakai (Live). Properti `b` yang mati tidak akan dihapus.
   - Alasan Pembatasan: Menghapus properti objek secara statis sangat berbahaya di JavaScript karena objek sering dimutasi secara dinamis atau dikirimkan via API (contoh: JSON.stringify). Bundler raksasa seperti Webpack pun umumnya menghindari tree-shaking properti internal objek demi keamanan.

2. Mutual Recursion (Rekursi Silang / Lingkaran Setan)
   - Masalah: Jika Fungsi A memanggil Fungsi B, dan Fungsi B memanggil Fungsi A, tetapi tidak ada satupun pemanggilan dari luar mereka berdua, secara logika mereka berdua adalah Dead Code. Namun engine akan menganggap mereka saling membutuhkan (Live) karena sistem pencocokan referensi antar Scope.
   - Solusi Teoritis: Menggunakan "Reachability Graph" (Graf Ketercapaian) dengan menelusuri rute eksekusi langsung dari akar/global. Ini adalah pengembangan masa depan yang bagus untuk disarankan (Future Work).

3. Constant Propagation / Data-Flow Analysis
   - Masalah: Engine hanya mengevaluasi nilai literal langsung (seperti if(false)), namun gagal melacak alur data variabel. Contoh: `const isDebug = false; if(isDebug) { ... }`. Blok 'if' ini secara logika adalah dead code, namun engine akan menganggap 'isDebug' dipakai, sehingga blok di dalamnya tidak dihapus.
   - Alasan Pembatasan: Membangun Control Flow Graph (CFG) yang sanggup mengingat status state variabel adalah materi Compiler Theory tingkat lanjut yang melebihi ruang lingkup skripsi S1.

4. Ketergantungan Titik Masuk (Multi-Entry HTML) [SUDAH DISELESAIKAN ✅]
   - Masalah Lama: Engine gagal membaca file yang tidak terdaftar di package.json, menganggap script terpisah (seperti custom script di HTML) sebagai Dead Files secara keliru.
   - Status Penyelesaian: Telah diselesaikan secara sempurna pada 23 April 2026 melalui fitur 'Custom Entry Points' pada .deadkillerrc.json. Pengguna kini bebas menentukan Node Akar secara manual.
